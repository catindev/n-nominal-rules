# Набор приемочного тестирования пакета правил FL_RESIDENT

**Версия документа:** 1.0
**Актуально для:** FL_RESIDENT rules package v3.1

## 1. Источник тестовых данных

### 1.1 Происхождение данных

Тестовый набор основан на реальных выгрузках бенефициаров номинального счета одного из мерчантов банка. Исходный Excel-файл содержит производственные данные, используемые банком в операционной деятельности.

Использование реальных данных позволяет:

- проверить жизнеспособность пакета правил на реальных бизнес-кейсах
- исключить искажения, возникающие при синтетических тестовых данных
- предоставить бизнес-подразделениям понятную и узнаваемую основу для приемочного тестирования

### 1.2 Ограничения исходных данных

Исходный файл является отчетной выгрузкой, а не API-контрактом. В связи с этим были выполнены преобразования:

| Ограничение исходника             | Способ обработки                                 |
| --------------------------------- | ------------------------------------------------ |
| Паспорт представлен одной строкой | Разделен на структурированные поля               |
| Адрес представлен текстом         | Приведен к полям countryCode и строковому адресу |
| Контакты агрегированы             | Разделены на phone / email                       |
| Отсутствуют служебные поля API    | Добавлены технические идентификаторы             |

### 1.3 Методика подготовки payload

Формирование тестовых запросов выполнялось по принципу:

**Источник → Нормализация → Минимальное техническое обогащение**

Где:

- _Нормализация_ это приведение данных к формату API
- _Техническое обогащение_ это добавление обязательных полей, отсутствующих в исходнике

Содержательная часть данных при этом не изменялась.

## 2. Описание тестовых сценариев

### 2.1 Логика построения набора

Набор покрывает:

1. Позитивные сценарии - корректные данные проходят проверки
2. Негативные сценарии - изолированная мутация (изменение) одного поля вызывает срабатывание конкретного правила
3. Регуляторные блокировки - проверки уровня EXCEPTION

Каждый негативный сценарий построен по принципу:

> Один сценарий = одно намеренное нарушение

Это позволяет однозначно связать результат с конкретным правилом.

## 3. Нюансы интерпретации результатов

### 3.1 Поведение статусов движка

| Уровень правила | status    | control  |
| --------------- | --------- | -------- |
| ERROR           | OK        | CONTINUE |
| EXCEPTION       | EXCEPTION | STOP     |

Статус `OK` при ошибках уровня ERROR означает наличие ошибок данных без регуляторной блокировки.

### 3.2 Множественные ошибки

Некоторые сценарии вызывают каскад правил. Это нормальное поведение движка правил. Например консистентность документа может дополнительно активировать блок foreign-tax

### 3.3 Телефонные номера

Телефоны сохранены в формате исходных данных (без кода страны). Формат допустим для текущего пакета правил, но для промышленной интеграции рекомендуется формат E.164.

### 3.4 Отличия Postman и Newman

В коллекции ожидания вынесены в collection-level переменные для корректной работы в Newman CLI.

## 4. Открытые вопросы и ограничения

| Область                 | Описание                                              |
| ----------------------- | ----------------------------------------------------- |
| Внешние реестры         | Проверка дублирования ИНН вне scope движка            |
| Справочники гражданства | Нет подключения к справочникам ЦФТ                    |
| Модель адреса           | Почтовый адрес представлен строкой                    |
| Контекст дат            | Проверка <= текущей даты реализована через workaround |

Эти ограничения задокументированы и не влияют на корректность приемочного тестирования.

## 5. Назначение набора

Коллекция предназначена для:

- Приемочного тестирования бизнес-подразделениями
- Демонстрации полноты покрытия требований
- Регрессионного тестирования пакета правил
- В перспективе для автоматизированных проверок через CI/CD

## 6. Критерии успешного прохождения ПА

Тестирование считается успешным, если:

1. Все позитивные сценарии проходят без ошибок
2. Все негативные сценарии вызывают ожидаемые правила
3. Регуляторные проверки корректно блокируют операции
4. Нет непредусмотренных срабатываний правил
