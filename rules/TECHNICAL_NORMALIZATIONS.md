# Технические нормализации и допущения пакета правил FL_RESIDENT

Этот файл фиксирует технические интерпретации бизнес-требований для текущего пакета правил.
Он не участвует в исполнении движка и не должен использоваться рантаймом как источник логики.
Его назначение — объяснить, почему отдельные машиночитаемые поля и проверки выглядят именно так.

## 1. Нормализация адресного foreign-trigger

В БТ условие включения foreign-блока сформулировано по смыслу:
- в адресе регистрации передан адрес не РФ;
- и/или в почтовом адресе передан адрес не РФ;
- и/или документ относится к иностранному документу.

Для целей машиночитаемой валидации это условие нормализовано в следующие технические атрибуты:
- `beneficiary.address.registration.countryCode`
- `beneficiary.contacts.postalAddressCountryCode`
- `beneficiary.idDoc.isForeignIdDoc`

Эти поля являются техническим представлением бизнес-требования и не означают, что в БТ они заданы как самостоятельные пользовательские параметры именно в таком виде.

Допущение текущей версии пакета правил: если заполнен `beneficiary.contacts.postalAddress`, то должен быть заполнен и `beneficiary.contacts.postalAddressCountryCode`. Это решение принято для того, чтобы техническая нормализация foreign-trigger оставалась однозначной и ближе к тексту БТ про почтовый адрес не РФ.

## 2. Что считается источником истины для foreign-trigger

Для ветки `FL_RESIDENT` foreign-блок включается только по одному или нескольким из следующих фактов:
- `beneficiary.address.registration.countryCode != RU`
- `beneficiary.contacts.postalAddressCountryCode != RU`
- `beneficiary.idDoc.isForeignIdDoc = true`

Поле `beneficiary.tax.foreignTaxResident` намеренно не используется как триггер foreign-блока в этой ветке.
Оно исключено из сценария `FL_RESIDENT`, чтобы движок правил оставался на уровне проверок, а не хранил агрегированную логику маршрутизации.

## 3. Интерпретация требования про адрес в иностранном государстве

В БТ используется формулировка:
- адрес места фактического проживания в иностранном государстве;
- или почтовый адрес в иностранном государстве;
- либо информация о его отсутствии.

Формат передачи «информации о его отсутствии» в БТ явно не определён.
Чтобы не усложнять текущий контракт искусственными параметрами, в пакете правил принято следующее техническое упрощение:

Требование считается выполненным, если заполнено хотя бы одно из полей:
- `beneficiary.tax.foreignResidencies[0].address`
- `beneficiary.contacts.postalAddress`

Отдельный специальный параметр для фиксации отсутствия адреса в текущем контракте не вводится.
Это решение является технической интерпретацией текущей версии БТ и может быть пересмотрено при уточнении контракта.

## 4. Soft-check поля `beneficiary.idDoc.issuer`

Проверки качества заполнения поля `beneficiary.idDoc.issuer` реализованы как `WARNING`, а не как `ERROR`.
Это сделано сознательно: задача данных правил — подсветить возможные проблемы качества данных, а не блокировать сценарий.

Для soft-check по символам используется консервативный whitelist допустимых символов:
- буквы кириллицы и латиницы;
- цифры;
- пробел;
- дефис;
- точка;
- символ `№`;
- слэш `/`.

Все остальные символы трактуются как потенциально мусорные и должны приводить к предупреждению.

## 5. Runtime context для датовых сравнений

Проверки вида «дата выдачи документа не должна быть больше текущей даты» используют только runtime context:
- `$context.currentDate`

Движок не вычисляет текущую дату самостоятельно.
Отсутствие `currentDate` считается технической ошибкой вызова сценария, а не ошибкой данных бенефициара.

## 6. Открытые вопросы

1. Требует подтверждения на бизнес-данных выбранный whitelist для soft-check поля `beneficiary.idDoc.issuer`. Сейчас он реализован консервативно и может потребовать калибровки по реальным значениям органов выдачи.
2. Интерпретация требования про «адрес ... либо информация о его отсутствии» реализована как техническое упрощение без отдельного атрибута отсутствия адреса. Если бизнесу потребуется явная фиксация отсутствия адресной информации, контракт придётся расширить отдельным полем или кодом причины.
3. `countryCode` и `postalAddressCountryCode` считаются технической нормализацией адресного foreign-trigger. Если в будущем модель входных данных изменится, эти поля могут быть заменены другой формой передачи того же бизнес-смысла без изменения общей логики foreign-trigger.
